# Завод роботов — полное описание решения

**Статус:** рабочая версия проверена локально; на GitHub ничего не публиковалось. Официальный API-check, practice-прогон и сверка с официальным движком не выполнялись. Все числа ниже — локальный эмулятор, а не результаты арены.

## 1. Что это

HTTP-сервис, который управляет виртуальным заводом по API v1: принимает поставки, запускает станки, собирает и продаёт роботов. Арена вызывает сервис, присылает `start`, затем события и `finish`; сервис отвечает командами. В комплекте — собственный эмулятор мира, локальный бенчмарк и веб-дашборд.

Стек: JavaScript, Node.js 18+ (проверено на v24.20.0), без внешних зависимостей.

## 2. Быстрый старт

```sh
PORT=4001 node src/server.mjs      # API и дашборд
# или
npm start                          # порт 8080 по умолчанию
```

- `GET /v1/health` → `{"status":"ok"}`
- Дашборд: `http://localhost:PORT/` (по умолчанию `http://localhost:8080/`).
- `ENABLE_DASHBOARD=0` отключает `/`, `/api/*` и `/api/simulate`; API арены продолжает работать.

## 3. Архитектура и файлы

| Файл | Назначение |
|---|---|
| `src/server.mjs` | HTTP-слой: маршруты, CORS, идемпотентность, телеметрия, лимиты, дашборд |
| `src/bot.mjs` | модель покупателей, выбор предложений, приём поставок, продажи, утилизация |
| `src/s04-planner.mjs` | ограниченный прогноз производства |
| `src/engine.mjs` | локальный эмулятор: мир, события, выполнение команд, `report`, отчёт |
| `web/index.html` | дашборд: прибыль, склад, станки, обучение по покупателям |
| `cli.mjs` | локальный бенчмарк |
| `tests/` | unit, сценарные и HTTP-проверки |

Поток одного события: арена → `server.mjs` → `FactoryBot.handleEvent` → `planProduction`/`planBestOffers` → команды → ответ. Состояние хранится по `runId`; после `finish` бот освобождается.

## 4. API-контракт

### Маршруты

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/v1/health` | `200 {"status":"ok"}`, до 3 с |
| `POST` | `/v1/runs/{runId}/start` | `200 {"ok":true}` |
| `POST` | `/v1/runs/{runId}/event` | `200 {"commands":[...]}` |
| `POST` | `/v1/runs/{runId}/finish` | `200 {"ok":true}` |

`start` содержит параметры мира: `horizon`, `eventTimeoutMs`, `capacity`, `storageFee`, `offerFee`, `buyerCooldown`, `priceCeiling`, `buyers`, `attributes`, `machines`. Решение берёт их из `start`, а не из примеров.

Событие: `{seq, t, event, state, report}`. Типы: `supply`, `machine_done`, `sale_result`, `idle`. В `state`: `cash`, `storage.capacity/free/items`, `machines[].busyUntil`, `buyers[].cooldownUntil`. `report` — результат предыдущего ответа: `{cmd, ok, reason?}`.

### Команды

| Команда | Поля | Смысл |
|---|---|---|
| `accept` | `itemId` | принять текущую поставку |
| `start` | `machineId, opId, itemIds` | запустить операцию; порядок входов как в `start` |
| `offer` | `buyerId, itemId, minPrice?` | предложить робота; комиссия списывается всегда |
| `discard` | `itemId` | удалить предмет со склада |

Не более 50 команд; выполняются по порядку и сразу. Снимок `state` относится к моменту до команд. Предмет уникален; каждый работающий станок резервирует место под результат. Недопустимая команда пропускается с записью в `report`, остальные выполняются.

### Идемпотентность и изоляция

- Повтор `runId + seq` возвращает сохранённый ответ, в том числе после `finish`.
- Новый `seq` для завершённого прогона → `409 run_finished`.
- Знания покупателей не переносятся между `runId`; после `finish` состояние бота освобождается.
- Команда без `start` создаёт состояние по умолчанию; арена всегда присылает `start`.

### Ошибки, CORS, лимиты

- Ошибка: `{"error":{"code":"...","message":"..."}}`; `400` — некорректный JSON/тело, `409` — завершённый прогон, `413` — тело больше 2 МБ, `404` — неизвестный маршрут.
- CORS: `Access-Control-Allow-Origin: *`, методы `GET/POST/OPTIONS`, заголовки `Authorization, Content-Type, X-Arena-*`, `Access-Control-Allow-Private-Network: true`; `OPTIONS` → `204`.
- Локальная конфигурация не проверяет Bearer-токен; для публичного доступа нужен прокси/аутентификация.
- `/api/simulate` принимает `seed` (целое 0..2³²−1) и `horizon` (1..2000); иначе `400`.

## 5. Стратегия

### 5.1. Модель покупателя

Шесть архетипов: `{red, green, blue} × {handles: true/false}`. Для каждого покупателя — шесть гипотез с интервалами `pMaxLo..pMaxHi` (цена точного совпадения) и `fLo..fHi` (коэффициент за одно несовпадение).

Допущения v1: `Pmax ∈ [45, 75]`, `f ∈ [0.30, 0.60]`, веса гипотез равны; цена точного совпадения `Pmax·(1±0,02)`, одного несовпадения `Pmax·f·(1±0,02)`, двух — 0.

Обновление:
- **продажа** даёт цену: интервал `Pmax` сужается; для несовпавших гипотез сужаются `f` и произведение `Pmax·f`; гипотеза с двумя несовпадениями закрывается;
- **отказ по цене** даёт верхнюю границу; cooldown и недопустимая команда ценой не считаются;
- **отказ на нижней границе** закрывает гипотезу, только если она несовместима с порогом с учётом возможного округления цены. При пороге с долями копейки сохраняется запас на округление;
- при противоречии модель не затирается: сохраняется предыдущая и увеличивается счётчик.

### 5.2. Выбор предложения

Полезность пары: `prob2 · expected2Price − offerFee` плюс надбавка. Код проверяет `buyer.uncertainty`, хотя неопределённость возвращается как `ev.uncertainty`, поэтому интерпретация надбавки как выбора между подтверждением и разведкой требует отдельной проверки. `minPrice` — фильтр, а не цена: покупатель платит свою цену. В конце смены (`ticksLeft ≤ 18`) или при переполнении склада разрешена продажа 1-совпадения по ставке 13.

Паросочетание — перебор до первых шести роботов склада и всех свободных покупателей; один робот и один покупатель не используются дважды; занятые исключаются по `cooldownUntil`.

### 5.3. Производство

Планировщик берёт фактические операции `start`, поддерживает резку, ручки, покраску и сборку. На событие — не более одной команды каждого типа, приоритет от сборки к резке. Учитывает склад, резерв места, занятость станков, предметы в обработке, длительности, стоимость, доступность покупателей и остаток горизонта. Будущие поставки не используются. Бюджет: 1024 кандидата и 5 мс; при исчерпании — пустой производственный план. Каждая лишняя копия архетипа штрафуется на 20; частичная резка/покраска допускается, если из текущих предметов ещё можно собрать робота.

### 5.4. Поставки и склад

Принимаются `sheet` и `control` при наличии места и времени на минимальный маршрут; ветки листов и контроллеров балансируются. При одном свободном месте лист отклоняется, контроллер — только если сразу доступна сборка. Цена поставки в v1 фиксирована (4/3) и не используется. Неликвид и переполнение — через `discard`.

### 5.5. Ограничения стратегии

Только v1: шесть архетипов, стандартная цепочка станков, фиксированные цены поставок. `start.attributes` и произвольные операции не обобщаются. Граница `cooldownUntil` трактуется как «такт уже доступен»; в ТЗ есть неоднозначность. Планировщик использует wall-clock, поэтому при экстремальной нагрузке возможна редкая недетерминированность.

## 6. Эксперименты и результаты

### 6.1. Методика

- База: замороженная S06 (`experiments/next/baseline/`, хэш `b3b8514f…`), идентичная рабочему боту до Ф1.
- Наборы: tune `(3000+i)·1013`, i=1..300; check `(4000+i)·1013`, i=1..200; final `(5000+i)·1013`, i=1..500. Горизонт 600; наборы не пересекаются; final запущен один раз.
- Сравнение: парные разницы по мирам, bootstrap-CI среднего (10 000 ресемплов, фиксированный seed), независимые худшие децили каждой стратегии. Исторический парный показатель на худших мирах базы приводится отдельно.
- Критерии: средний выигрыш ≥ 1 %, нижняя граница CI95 > 0, худший дециль не хуже базы более чем на 2 %, ноль недопустимых/ошибок/таймаутов, p99 < 50 % `eventTimeoutMs`.

### 6.2. Итоговые числа

Таблица относится к сохранённой Ф1 до последнего исправления округления (`experiments/next/review-baseline/`). Текущая версия отличается; повторная финальная оценка не проводилась. На 300 настроечных мирах её средняя парная разница с сохранённой Ф1 — +0,013, медиана 0, совпало 299 миров.

### 6.3. Что проверялось и отклонено

- **Ф1** — отказ на нижней границе ставки закрывает гипотезу точного совпадения. Принято на tune, check и final.
- **S11a** — отключение надбавки дало +4,14 (+0,05 %), CI95 [−4,11; 12,78]. Поскольку код обращается к `buyer.uncertainty`, а оценка возвращает `ev.uncertainty`, интерпретация различий надбавок требует отдельной проверки.
- **S11b** — исправленная политика задержки зонда на настройке дала −97,19 в среднем относительно текущего бота. Это эффект политики в целом, а не отдельная оценка ценности информации; прежний вариант также мог отбрасывать допустимые подтверждённые пары.
- **S04** — не даёт измеримого преимущества над S06; прежняя оценка −1,2 на review-наборе подтверждается.

### 6.4. Ограничения измерений

Локальный эмулятор не сверен с официальным; официальные ориентиры (≈5 970 / 7 740) к локальным числам неприменимы. Поток ценового шума зависит от числа предложений, поэтому парные разницы не идеально изолированы; вывод подтверждён на трёх независимых наборах. Сеть и HTTP-задержка не замерялись на арене.

## 7. Проверки

```sh
npm test           # 135 тестов: эмулятор, бот, планировщик, observer, манифест, Ф1, review-регрессии
npm run test:http  # 5 HTTP-тестов: контракт, CORS, ошибки, лимиты, полная смена
npm run test:all
```

HTTP-тест полной смены (`tests/http-full-shift.mjs`) прогоняет 60 тактов локально, затем воспроизводит те же 113 событий через рабочий сервер и сравнивает команды побайтно; проверяет повтор `seq` после `finish` и отключение дашборда через `ENABLE_DASHBOARD=0`. Профильные тесты подтверждают: ноль недопустимых команд, корректный `report`, изоляцию `runId`, резерв склада, `props`/`inherit`, cooldown, отказ по цене, идемпотентность.

5-мирный бенчмарк (`node experiments/benchmark.mjs tune 5`) на принятой версии: **9 005,52** средней прибыли, 0 ошибок/таймаутов/недопустимых команд.

## 8. Интерфейс

Дашборд показывает:
- прибыль по тактам и текущий баланс;
- загрузку станков;
- заполненность склада (kind, цвет, ручки);
- таблицу обучения покупателей: кандидаты, диапазон `Pmax`, продажи;
- кнопку локальной симуляции с выбором seed и горизонта;
- сравнение с наивным ботом для локального прогона.

## 10. Ограничения и открытые вопросы

- Нет официального API-check, practice-прогона и сетевого замера; результат на арене не подтверждён.
- Локальный движок не эквивалентен официальному; расхождения: `priceCeiling` по умолчанию, отсутствие `invalidCommandFine`, `maxTimeouts` задаётся локально, шум цен использует общий RNG.
- Поддержан только v1; расширение свойств/станков потребует переработки модели и планировщика.
- Граница `cooldownUntil` и условная обязательность `price`/`reason` в `sale_result` остаются вопросами к организаторам.
- Публичный адрес должен быть доступен из интернета; локальная конфигурация не проверяет Bearer-токен и разрешает любое происхождение — это только для разработки.
- Внутренние планы, ТЗ и отчёты S01–S12 не публикуются; это решение команды, а не свойство кода.

## 11. Итоговое решение

Историческая Ф1 дала +4,16 % на финальных 500 локальных мирах. Рабочая версия после неё исправлена для дробных порогов и проверена на настройке; ей нельзя приписывать прежний финальный результат. Официальная сверка и независимая финальная оценка исправленной версии остаются открытыми.
