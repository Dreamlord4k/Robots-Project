# Завод роботов · ИРИТ-РТФ

Решение проекта «Завод роботов»: HTTP-сервис по спецификации v1, алгоритм планирования
производства и продаж (уровень 3), собственный эмулятор арены, дашборд и тесты.
Node.js 16+, **без внешних зависимостей**.

```
server.mjs       HTTP-сервис арены (health / start / event / finish) + CORS + лог + эмулятор для дашборда
bot.mjs          алгоритм: конфиг мира, модель рынка, планировщик, уровень 1 и уровень 3
engine.mjs       эмулятор арены (правила v1) + генератор миров по seed
cli.mjs          бенчмарк: node cli.mjs --seeds 20
test.mjs         юнит-тесты планировщика и обучения цен + интеграционный прогон
web/index.html   дашборд: деньги по тактам, станки, склад, продажи, покупатели
logs/            журнал прогонов (jsonl, создаётся автоматически)
```

## Запуск

```bash
node server.mjs                       # сервис на http://localhost:4001
# в другом терминале:
node cli.mjs --seeds 20               # бенчмарк: наивная / наша / оракул
node test.mjs                         # тесты
```

Дашборд: откройте <http://localhost:4001/> — он сам берёт данные из `/v1/sim/run`.
Песочница ИРИТ-РТФ: адрес сервиса `http://localhost:4001`. Публичный адрес для раунда —
любой хостинг или туннель (`cloudflared tunnel --url http://localhost:4001`).

Переменные окружения: `PORT`, `ARENA_TOKEN` (если задан — требуется
`Authorization: Bearer …`), `LOG_DIR`, `VERBOSE=0` (тихий режим).

## Протокол

| Метод | Ответ |
|---|---|
| `GET /v1/health` | `{"status":"ok"}` |
| `GET /v1/info` | `{"name","version","project","specVersion"}` |
| `POST /v1/runs/{runId}/start` | `{"ok":true}` — создаёт состояние прогона и бота |
| `POST /v1/runs/{runId}/event` | `{"commands":[…]}` — идемпотентно по `seq` |
| `POST /v1/runs/{runId}/finish` | `{"ok":true}`, закрывает журнал |

* `OPTIONS` → `204` с `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Headers: *`,
  `Access-Control-Allow-Private-Network: true` (нужно песочнице браузера).
* Состояние хранится отдельно на каждый `runId`; знания между прогонами не переносятся.
* Любая ошибка разбора → `{"commands":[]}`, никогда не `5xx`. Ответ синхронный,
  локально < 5 мс (лимит 2000 мс, мы логируем «медленные» ответы > 200 мс).
* Кэш идемпотентности: `seq → JSON ответа`, повтор отдаёт тот же байт-в-байт ответ.
* Журнал `logs/run-<id>.jsonl`: событие, команды, report, время ответа, заголовки арены.

## Стратегия (уровень 3)

### 1. Ключевое наблюдение про `minPrice`

`minPrice` в `offer` — не цена сделки, а только порог «согласен/нет»: покупатель всегда платит
**свою** цену, если она ≥ `minPrice`. Отсюда:

* `minPrice = 0` — отдаём робота бесплатно, если робот попал на «нулевую» ступень покупателя;
* `minPrice = 15` (себестоимость) — теряем всю f-ступень: она начинается с `45·0.3 = 13.5`;
* **`minPrice = 2`** — отсекает только нулевую ступень, а фактическую цену покупателя мы
  всё равно узнаём из `sale_result` (в нём есть `price`).

Поэтому «обучение цен» — это не бинарный поиск по вилке, а **прямое наблюдение цены**
плюс достройка остальных ступеней из структуры правила.

### 2. Модель рынка

Для каждой пары (покупатель, тип робота) из 6 типов (`цвет × ручки`) хранится:

* `sample` — опознанный образец (цвет + ручки), `null` пока неизвестен;
* `pmax` — оценка максимальной цены;
* `ftier` — наблюдённая цена «одно расхождение» = `Pmax·f`;
* `tested[key]` — наблюдённая цена или `null` (отказ на нашем `minPrice`).

Обновление:

| Событие | Вывод |
|---|---|
| `sold price = p ≥ 44` | это образец: `sample = тип`, `Pmax ≈ p / 0.99` |
| `sold 0 < p < 44` | `Pmax·f = p`, и это значение верно для **всех** типов с одним расхождением |
| `refused (below_min_price)` | тип не образец; если цена была ≤ 2, у покупателя на нём 0 |
| `refused (cooldown)` | информации нет, модель не трогаем |

Оценка цены непроверенной пары — `22`: математическое ожидание дохода по типам при
`Pmax ≈ 60`, `f ≈ 0.45` (совпадение 1/6 → 60, одно расхождение 1/2 → 27, два — 0).

**Главная оптимизация против эталонной «обучающейся»:** одна сделка на «чужом» типе даёт
`Pmax·f` сразу для всех пяти остальных типов того же покупателя — их не нужно зондировать
по отдельности. Аналогично, продажа на «своём» типе мгновенно оценивает все f-ступени.

### 3. Планировщик

Порядок обработки каждого события:

1. **Поставка.** Принимаем, если `free ≥ 2`, остаток смены позволяет достроить цепочку,
   и вид ещё нужен (`sheet < 2` шт., корпусов < 3; `control < 2` шт.).
   Сразу после `accept` в том же ответе запускаем резку, если станок свободен.
2. **Сборка** — приоритет: `max(оценка цены)` по окрашенным корпусам, `itemIds = [body, control]`.
3. **Ручки** — только если лучший тип с ручками выгоднее бесручечного больше, чем стоит операция.
4. **Покраска** — пара (корпус, цвет) с максимальным «желанием»; дубли по типу штрафуются
   на 6 за каждую единицу уже произведённого, чтобы не копить неликвид.
5. **Резка** — держим буфер корпусов (не больше 3, иначе склад забивается телами).
6. **Продажи.** Робот → покупатель с максимальным счётом `оценка + 12·(зонд?)`, только
   если тот свободен (`cooldownUntil ≤ t`). Один `offer` на робота в ответе, после `offer`
   покупатель локально помечается занятым до `t + 8`.
   Если покупатель занят дольше 6 тактов, а через него робот стоит на 4+ дороже — предложение
   **откладывается** (робот подождёт в очереди, хранение 0.5/такт дешевле потери 35 монет).
7. **`discard`** — если для типа у всех покупателей образец известен и оценка ниже `minPrice`
   (иначе робот занимает место и платит 0.5/такт до конца смены).

Желание типа = `max по покупателям (оценка − себестоимость − 1.5)` плюс информационная
надбавка `5 × (число неизвестных образцов)`, пока тип не проверен — это и есть exploration.

### 4. Дисконт горизонта

Цепочка не запускается, если до конца смены не остаётся времени:
сборка — 5 тактов запаса, покраска — 8, ручки — 10, резка — 10; поставки не принимаются,
когда разрез уже не имеет смысла. Это убирает закупки «в пустоту» в последние такты.

### 5. Почему это работает

Узкое место — покраска и сборка (3 такта), максимум ≈ 200 роботов за смену; лимит поставок
листов/контроллеров — тоже ≈ 200 штук каждого. Поэтому прибыль почти целиком определяется
**средней ценой сделки**: наивная стратегия получает в среднем 23.5 за робота (случайный тип),
наша — целенаправленно делает типы, попавшие в образцы (60+), и добирает f-ступень (27)
только чтобы не простаивали покупатели. Отсюда разрыв с наивной в разы.

## Запуск бенчмарка

```bash
node cli.mjs --seeds 20                 # наивная / уровень 3 / оракул
node cli.mjs --seeds 20 --verbose       # по каждому миру
node cli.mjs --seeds 5 --strategy level3 --horizon 300
```

Вывод — средняя прибыль, ±sd, минимум/максимум, число продаж, число недопустимых команд
и худшее время ответа. Ориентиры спецификации (v1, 20 миров): наивная ≈ 1450,
обучающаяся ≈ 5970, оракул ≈ 7740. Цифры зависят от реализации эмулятора и мира,
поэтому сравнивать нужно свои прогоны между собой на одних и тех же seed'ах:
`cli.mjs` гоняет все три стратегии на одном наборе миров.

## Тесты

`node test.mjs` — 18 проверок:

* конфиг мира: мусор на входе, восстановление станков по умолчанию;
* обучение цен: структура `{Pmax, Pmax·f, 0}`, опознание образца, перенос f-ступени
  на непроверенные типы, отказ закрывает пару, `cooldown` не портит модель;
* планировщик: `accept` + `start` в одном ответе, запрет приёмки при `free < 2`,
  порядок `itemIds` в сборке, сборка только с окрашенного корпуса, `offer` только
  свободному покупателю и с `minPrice > 0`, отсутствие действий на горизонте,
  идемпотентность по `seq`, устойчивость к кривому входу;
* эмулятор: 0 недопустимых команд, ответ < 50 мс, продажи > 20;
* бенчмарк 5 миров: уровень 3 прибыльнее 1000 и валиден.

## Частые ошибки, которые здесь закрыты

* перепутанный порядок `itemIds` в `assemble` — бот всегда ставит `body` первым;
* запуск операции на предмете, который в этом же ответе уже ушёл на другой станок —
  зеркало склада удаляет предмет сразу при планировании команды;
* `offer` покупателю на паузе (комиссия списывается, продажи нет) — проверка
  `cooldownUntil ≤ t` перед каждой командой;
* забытый `discard`, из-за которого склад забит неликвидо́м — выброс типов, которые
  ни один покупатель не возьмёт;
* долгий ответ — вся логика синхронная и работает на готовом снимке `state`.

## Что дальше (v2)

`parseWorld` не привязан к идентификаторам v1: станки, операции, цвета и число покупателей
читаются из сообщения `start`, типы и себестоимость считаются из `machines`/`prices`.
Больше станков, свойств и покупателей подхватится без правок модели рынка — править нужно
только эвристики приоритетов (`desire`, `wantHandles`, запас по тактам).
